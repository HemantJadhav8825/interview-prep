🔹 BLOCK 5: Tech lead round
You have 6 engineers: 2 seniors 3 mid-level 1 junior but Delivery is slipping, and code quality is degrading. What do you do in the first 30 days?

In the first 30 days, I’d focus on stabilizing before accelerating. I’d start by diagnosing the real problems—reviewing recent code, bugs, and missed deadlines, and running 1:1s to identify patterns—while freezing non-essential work to stop quality from slipping further. Next, I’d create clarity by defining ownership (seniors over systems, mids over features, the junior on well-scoped tasks), enforcing consistent PR reviews, and setting a clear definition of done. With that structure in place, I’d improve execution by limiting work in progress, breaking work into smaller pieces, making blockers visible, and having senior engineers pair and review early to unblock others. Finally, I’d raise the bar carefully by fixing one or two high-impact quality issues and resetting expectations with stakeholders around more predictable delivery.

What exactly do you look for in the code review to “diagnose” problems?

I review code using a simple flow: Correctness → Boundaries → Change Risk. First, I check whether the code actually works and whether it relies on hidden assumptions or only handles the happy path. Next, I look at boundaries—whether responsibilities are clearly separated, dependencies point in the right direction, and state changes are easy to understand. Finally, I assess change risk: how hard it would be to modify, extend, or confidently ship this code. In short, does it work, is it well separated, and how painful will the next change be?
